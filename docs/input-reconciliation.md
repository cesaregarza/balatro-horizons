# Balatro Horizons: handoff and Claude input reconciliation

Prepared 2026-09-14. Status: proposed synthesis for review. Implementation remains paused at the owner's request. This document records how to incorporate the research input; it does not authorize resuming the build or amend the original specification. The existing scaffold is provisional and unverified.

Inputs: the original [implementation contract](contract/balatro_horizons_spec/BALATRO_HORIZONS_SPEC.md), its [agent handoff](contract/balatro_horizons_spec/AGENT_HANDOFF.md), and the preserved [Claude research input](contract/claude-research-input.md). The Claude document is user-supplied research, with a mixture of source claims, proposals, and acknowledged estimates.

The recommended project remains a full-run Balatro evaluation harness with an expert review workbench. Its research question is whether agents coordinate immediate scoring, survival, and development across decisions. Full-run autonomous success supplies the primary outcome; inspectable decisions, prospective annotations, and certified intervention branches supply diagnostic evidence. The proposed automatic horizon sub-scores in Claude's note would need a separate validation argument before becoming benchmark scores.

Three narrow source checks support the engineering decisions above. These checks used current public pages on 2026-09-14; they are not immutable revision pins or live validation:

- BalatroBench's own description identifies average round reached as its main score and lists tool-call validity, token use, time, and cost. That establishes a concrete comparison point; it does not establish every negative claim made about the project in Claude's note. [BalatroBench methodology](https://balatrobench.com/about.html)
- BalatroBot documents JSON-RPC gameplay and save/load methods, but its GameState example also contains the seed and its API includes debug mutation methods. This supports an audited adapter and a strict public boundary. Documentation alone does not establish complete native action coverage or reliable restoration. [BalatroBot API reference](https://coder.github.io/balatrobot/latest/api/)
- The inspected BalatroLLM loop automatically selects a blind and automatically cashes out. Reusing that loop unchanged would remove choices the handoff requires us to audit and preserve. [BalatroLLM game-loop source](https://github.com/coder/balatrollm/blob/main/src/balatrollm/bot.py)

Claude's wider benchmark literature and adjacent-project inventory are useful research leads. Paper identifiers, publication venues, quantitative results, release versions, licenses, simulator coverage, throughput, community statements, and redistribution conclusions were not comprehensively verified in this reconciliation. They should enter a source ledger with an explicit verification status before appearing as project claims. Star counts and current leaderboard positions are unnecessary for the implementation decision.

The main addition to the research framing is an explicit separation among prior mechanics knowledge, exposure to particular seeds or trajectories, and assistance supplied by the harness. These threaten different interpretations and need different controls. Known mechanics do not make an unseen run trivial; unfamiliar names or rules do not by themselves isolate reasoning. Both documents motivate studying these questions, but neither supplies benchmark evidence that resolves them.

The handoff's ordering remains the recommended build sequence once work resumes: audit and environment lock; a labeled offline episode that can be recorded, reopened, and annotated; native action and information validation with empirical replay/checkpoint certification; full review and interventions; then authorized model batches and reporting. The research additions do not turn those gates into completed work.

Only documentation was added during this reconciliation. No application source, configuration, or dependency lock was changed; no tests, builds, game runs, or paid provider calls were made.
